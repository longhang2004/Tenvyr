# T05: Reuse AgentProcessor in a Strict HTTP Review Worker

## Delivered behavior and interfaces

1. **`StrictReviewRunner` (`io.tenvyr.reviewworker.StrictReviewRunner`)**:
   - Implements `AgentProcessor.Runner`.
   - Enforces strict JSON parsing via `JsonParser.Feature.STRICT_DUPLICATE_DETECTION`
     and `DeserializationFeature.FAIL_ON_TRAILING_TOKENS` on raw runner `data.output`
     *before* `AgentProcessor`'s lenient `parseOutput`.
   - Emits a stable sanitized parse error message (`"Agent Runner raw output is not strict JSON"`)
     on malformed JSON, duplicate keys, or trailing tokens, never concatenating `e.getMessage()`.
     This prevents raw source text, secrets, or Jackson parser excerpts from leaking into public
     callback error payloads.
   - Validates report structure strictly against `ReviewReportContract.requireOutput`:
     score must be an integer between 0 and 100, findings must be an array of at most
     50 non-blank strings (each &le; 1,000 UTF-16 units), serialized output must not
     exceed 65,536 UTF-8 bytes, and no unknown top-level properties are permitted.
   - Any validation failure throws `IllegalArgumentException`, mapping directly to
     non-retryable failure (`AGENT_EXECUTION_FAILED`) with output absent, strictly
     preventing fallback to legacy score 80 or 90.
   - Strict metadata validation: malformed non-null `data.metadata` fails nonretryably
     rather than being silently replaced with fabricated fields; `metadata.fallbackUsed`
     when supplied must be boolean; `usageSource`, `provider`, `model`, and `mode` when
     supplied must be textual (or null). Upstream `fallbackUsed: true` and configured
     transport mode truth are preserved. Null legacy metadata is normalized to absence
     only in `StrictReviewRunner`; shared `AgentProcessor` remains unchanged beyond its
     bounded runner factory, preserving legacy behavior.

2. **`ReviewWorkerMain` (`io.tenvyr.reviewworker.ReviewWorkerMain`)**:
   - `ReviewWorkerMain.configuration(Map<String, String> env)`: validates and builds
     frozen `WorkerConfig` with fixed bounds (`concurrency=2`, `maxQueuedRuns=16`,
     `maxRequestBytes=1,048,576`, `maxResponseBytes=65,536`, `agentName="code-reviewer"`).
   - Dedicated runner response bound: `FIXED_RUNNER_MAX_RESPONSE_BYTES = 1_048_576` (1 MiB),
     clearly named and decoupled from the Worker admission constant (`FIXED_MAX_REQUEST_BYTES`).
   - `ReviewWorkerMain.runner(Map<String, String> env)`: resolves mode:
     - `MOCK` (default): fixed truthful canned report (`score=100`, explicit finding
       stating no real source or security analysis was performed, mode `MOCK`, provider
       `mock`, model `demo-fixture`, `usageSource="unavailable"`, `fallbackUsed=false`,
       no invented token counts).
     - `RUNNER`: connects to fixed private Runner URL via bounded `AgentProcessor.httpRunner(runnerUrl, FIXED_RUNNER_MAX_RESPONSE_BYTES)`,
       wrapped in `StrictReviewRunner`. Never falls back to MOCK upon runner failure.
   - `ReviewWorkerMain.create(WorkerConfig config, AgentProcessor.Runner runner)`:
     hosts `AgentProcessor` inside `Worker` runtime. Maps processor success to bare
     business output passed to `context.success(output, usage, null, metadata)` and
     truthfully maps timeouts/failures to `context.fail`.
   - Wire assertion tightened: stalled-body and timeout failures map over Worker wire
     to exact status `failed` and error code `AGENT_TIMED_OUT`.

3. **Bounded `AgentProcessor.httpRunner(String runnerUrl, int maxResponseBytes)`**:
   - Added public bounded factory to `backend/agents/src/main/java/io/tenvyr/agents/AgentProcessor.java`.
   - Uses JDK-only `HttpClient` with `Redirect.NEVER`.
   - Enforces stream byte cap (1 MiB) before allocating or parsing JSON.
   - Remaining deadline bounds stalled response bodies as well as headers, throwing
     `HttpTimeoutException` within bounded elapsed time.
   - Preserves legacy private `httpRunner(String runnerUrl)` and legacy constructors
     unchanged so retained `AgentCheck` remains compatible.

## Worker bounds and operational limitations

- **Fixed concurrency and queue**: Concurrency is fixed at 2; max queued runs is 16.
  Excess requests receive 429 (`QUEUE_FULL`).
- **Process-local ephemeral state**: Runs, idempotency records, and execution queues are
  held in memory. Process restart discards in-memory history; new submissions receive a
  new `runId` and recompute. No durable Worker storage or Kafka dependency is claimed.
- **At-least-once callback delivery**: Worker retries failed callbacks (e.g. on 503)
  with exponential backoff and jitter, reusing identical serialized bytes and delivery ID.
