# T03: Sessions, CSRF, Current Actors and Explicit Bootstrap

Status: **Accepted locally on 2026-11-14 (Asia/Saigon)**. T00–T03 are the four
accepted tasks in the [active plan](../README.md). The controller records the
local checkpoint after final documentation, identity, and staged diff checks.

## Delivered behavior and interfaces

1. Standard Spring Security form login uses sessions: `POST /login` requires
   CSRF and returns 204 on success or safe 401 JSON on failed authentication.
   Standard logout requires CSRF, invalidates the session, clears its cookie,
   and returns 204. Session fixation defense changes the session ID; the CSRF
   strategy invalidates the token used before authentication.
2. `GET /api/v1/auth/csrf` permits anonymous access and returns
   `{headerName,parameterName,token}` with `Cache-Control: no-store`.
   Fetch a fresh token after login and logout. `GET /api/v1/me` returns the
   current `Actor`. Authentication/CSRF/role errors use
   `{code,message,requestId}`, with static messages and a UUID request ID.
   Only the exact signed callback POST is exempt from CSRF.
3. `ActorResolver(JdbcTemplate).current(Authentication)` rejects null,
   unauthenticated, and anonymous inputs before JDBC. Each lookup resolves
   the principal username to its durable UUID, current database role, and
   enabled state. Disabled or deleted users receive 401. The actual
   `JdbcUserDetailsManager` maps persisted roles to the exact
   `ROLE_SUBMITTER` or `ROLE_REVIEWER` authority, using the shared
   `JdbcTemplate` with a 5-second query timeout.
4. `BootstrapUsers.parse(Path)` returns `List<Entry>`, where
   `Entry(String username,String password,Role role)` describes the local
   manifest. A non-empty JSON array must contain exactly those string fields,
   lowercase ASCII usernames matching `[a-z0-9_.-]{1,64}`, nonblank supplied
   passwords, and one of the two roles. Missing files raise `IOException`;
   invalid content raises sanitized `IllegalArgumentException`.
5. Explicit bootstrap writes generated UUIDs and `{bcrypt}` password hashes
   in one Spring transaction. Existing usernames cause a clear conflict:
   their UUID/hash remains unchanged and earlier new entries roll back.
   The normal startup path creates no default users. Parser validation
   messages contain field/index information; raw JSON causes and failed
   insert details are not retained in startup errors.

## Lifecycle and operator use

The non-lazy bootstrap component depends on completed database initialization.
Its initializer finishes before SmartLifecycle recovery start and web admission.
Runtime adapters may already have been constructed while singleton beans are
initialized; bootstrap failure still closes managed resources. There is no
strict bootstrap-before-runtime-construction claim.

Create a private local JSON manifest using your own credentials and add
`--review.bootstrap-users-file=/absolute/private/users.json` to the configured
review application for the initial bootstrap. Missing credentials fail
validation. Do not commit the credential file. Remove the option for subsequent
normal starts; repeating it against existing users reports a conflict rather
than resetting them.

Local HTTP cookies are HttpOnly, SameSite=Lax, and explicitly Secure=false.
The `https` deployment profile sets Secure=true; an HTTPS listener or
TLS-terminating proxy supplies the transport. Sessions are held in memory, so an
application restart requires login again; persisted PostgreSQL rows survive.

| Included regressions | All T01/T02 review unit and integration suites passed in that run |

The meaningful acceptance evidence is:

1. Pre-login CSRF tokens receive 403 under the newly authenticated session;
   refreshed tokens perform the mutation. Both session IDs must exist and
   differ. Logout invalidates authentication and the old token, while a fresh
   anonymous token permits the next login.
2. The real JDBC user-details bean returns exact singleton authority sets.
   Current database enabled/role changes are enforced on an existing session.
   Query/body identity spoofing and owner/reviewer visibility are exercised
   through protected **test-only** fixtures.
3. User UUID snapshots before the first no-bootstrap startup prove there is no
   implicit seeding. Bootstrap conflict places a new entry before an existing
   one and proves rollback plus preservation of the existing UUID/hash.
   Failing child contexts never emit readiness and close their captured pool.
4. Malformed JSON secret markers and valid JSON containing invalid username or
   role markers are absent from exception/cause messages. The last two vectors
   first produced exactly two failures in 32 unit tests, then passed after the
   parser messages were sanitized.
5. Default local cookie flags and the active `https` profile's Secure flag are
   verified through HTTP responses. Fixture users have generated owned
   identities and cleanup uses exact IDs/names.

These fixtures do not establish authorization for the future business
repositories. T04 and T06 must repeat ownership, role, and visibility checks
against real review requests and commands. No new retained pure or SDK-suite
run is claimed for T03; the accepted [T02 evidence](T02.md) remains separate.
The full retained Kafka/polyglot compatibility suite remains a T08 gate.

## Reproduce

Run in Ubuntu WSL2 Bash from the repository root. The controller's fixture file
is ignored and contains private local credentials; another environment must
provide its own disposable PostgreSQL database and credentials.

```bash
. docs/_scratch/agy/T00/postgres.env
export POSTGRES_USER POSTGRES_PASSWORD
export TENVYR_REVIEW_TEST_DATABASE_URL='jdbc:postgresql://127.0.0.1:15432/tenvyr_review_test?sslmode=disable&currentSchema=public'
export JAVA_TOOL_OPTIONS=-Duser.timezone=UTC
sh scripts/review-checks.sh integration

node scripts/verify-docs.mjs
node scripts/verify-product-identity.mjs
```
